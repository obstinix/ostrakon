# Audit of Ostrakon

This is the audit log for Ostrakon. It lists the defects that commonly break blockchain voting DApps, what Ostrakon does about each one, and the evidence that the fix works. It also lists the findings from re-auditing Ostrakon itself (§3).

Evidence is in [VERIFICATION.md](VERIFICATION.md) unless noted. Severity scale: **Critical**, the system doesn't work or votes can be wrong. **High**, a correctness or security property is broken. **Medium**, a robustness or UX failure. **Low**, hygiene.

---

## 1. Checklist: build, contract, and frontend

### Build and tooling

| ID | Severity | Risk | Ostrakon | Evidence |
|---|---|---|---|---|
| B-01 | Critical | Automated tests don't run, or test a different contract | Foundry unit, fuzz, and invariant suites run by `npm test`, including 12 core voting scenarios | 111 Foundry tests, 21 Vitest, 22–23 Playwright per browser; all green from a clean clone |
| B-02 | Critical | The deployment address is written into a tool-managed folder and pruned by the next compile | Deployment goes to `web/public/deployment.json`, outside any tool's artifact folder, and is checked at runtime against code at the address | E2E stale/missing-deployment tests |
| B-03 | High | A fresh clone can't build because generated files are git-ignored but imported | The typed ABI is generated by `npm run dev` and `npm run build` | Clean-clone `npm ci` → `npm run build` exit 0 |
| B-04 | High | The build fails under CI lint settings | Lint is its own gate with zero warnings allowed | `npm run lint` (`--max-warnings 0`, `forge lint -D warnings`) exit 0 |
| B-05 | Medium | Running the app takes several terminals and manual steps | `npm run dev` starts the chain, deploys, seeds, generates the ABI, and starts the app | Manual run; VERIFICATION.md |
| B-06 | Medium | Docs and scripts disagree on which account is admin | No global owner; the seed script prints every role; `npm run keys` | Seed output |
| B-07 | Medium | `index.html` references files that don't exist | Fresh `index.html` with no dead references | 0 failed requests, 0 console errors on load |
| B-08 | Medium | Vulnerable or unused dependencies | Minimal dependency set (viem rather than web3.js) | `npm audit`: 0 vulnerabilities |
| B-09 | Low | Old compiler | solc 0.8.30, pinned in `foundry.toml` | `forge build` |

### Smart contract

| ID | Severity | Risk | Ostrakon | Evidence |
|---|---|---|---|---|
| C-01 | High | No phases: registering and voting at any time, nothing closes an election | `Registration → Voting → (Reveal) → Ended`, forward-only, optionally bound to timestamps | `PhaseTest` (14), `invariant_phaseMonotonic` |
| C-02 | High | No winner or finalization | `finalize` (anyone, after Ended) records the winner or a tie and emits `Finalized` | `FinalizeTest`, `testFuzz_finalizeMatchesArgmax` |
| C-03 | High | No input validation on elections | 2–32 unique, non-empty candidates of ≤ 64 bytes; name ≤ 80 bytes; custom errors | `CreateValidationTest` (10), `testFuzz_nameLengths` |
| C-04 | Medium | `address(0)` can be registered | `ZeroAddress` for single registration; skipped in batches | `test_singleRejectsZero`, `test_batchSkipsZeroAndAlreadyRegistered` |
| C-05 | High | Unbounded batch registration runs out of gas | `MAX_BATCH = 200`; the UI chunks longer lists; the Merkle allowlist replaces per-address registration for large electorates | Full batch 9.47M gas; `testFuzz_largeElectorate` (2–2,000 members) |
| C-06 | High | A single global owner that can't be transferred | Per-election admin with a two-step hand-over | `AccessControlTest`, `TwoStepAdminTest` |
| C-07 | Medium | A "private" voter list that events make public anyway | The voter list is a public paginated view, and the README says so | `getVoters` tests |
| C-08 | High (privacy) | No ballot secrecy | **Partly addressed.** Open ballots are public by design. Secret ballots (commit–reveal) hide choices and running totals until reveal; choices are public after reveal | `SecretBallotTest` (22), `invariant_secretBallot`, lifecycle and E2E runs |
| C-09 | Medium | Missing views force N+1 reads | `getTallies`, `getElections`, `getVoterStatuses`, `isRegistered`, `hasVoted`, `voterCount` | Unit tests |
| C-10 | Low | State changes without events | Nine events cover every state change | `vm.expectEmit` checks |
| C-11 | Low | Gas waste (zero writes, double checks) | No zero writes or redundant checks | `.gas-snapshot` |
| C-12 | Low | Revert strings and no NatSpec | Custom errors and NatSpec on every external function | Source |
| C-13 | Low | The admin can register and vote themselves | **Not addressed by design.** The admin controls eligibility; documented as a trust limitation with Sybil registration | SECURITY.md |

| ID | Severity | Risk | Ostrakon | Evidence |
|---|---|---|---|---|
| F-01 | Critical | Nothing renders without a wallet | Reads go through a public RPC client; the app works fully read-only | E2E read-only test |

## 2. Accepted limitations
- **C-08, ballot secrecy:** open ballots are public; secret ballots are only secret until reveal. Zero-knowledge secrecy is future work.
- **C-13, the admin controls eligibility** (Sybil registration, self-registration): inherent to the allowlist model, and documented as a trust limitation.
- **Identity binding:** out of scope.

## 3. Re-audit of Ostrakon (second round)

These findings come from re-auditing Ostrakon after the secret-ballot release. Each has the evidence that found it and its status.

| ID | Finding | How it was found | Status |
|---|---|---|---|
| R-01 | Single-step `transferAdmin`: a mistyped address took the election for good | SECURITY.md listed it as an accepted risk | **Fixed.** Nominate, then accept, with cancel. 8 tests; a one-step mutant is caught by 5 of them |
| R-02 | Large electorates needed one registration per address (≈47k gas each, paid by the admin) | C-05 above | **Fixed.** Merkle-root allowlist (OpenZeppelin format), voter-paid claims, frozen at voting. 14 tests, an invariant, and 2 E2E flows |
| R-03 | A lost secret-ballot receipt meant a lost vote | SECURITY.md commit–reveal weaknesses | **Mitigated.** The salt comes from a deterministic wallet signature, and "Recover with my wallet" rebuilds the receipt. E2E wipes the receipt and recovers it; a declined signature falls back to a random salt |
| R-04 | The connect button always used `connectors[0]` (the generic `window.ethereum` connector). With several wallet extensions it could connect whichever one had overwritten `window.ethereum`, and it failed for wallets that only announce via EIP-6963 | Code review of `useWalletController` | **Fixed.** EIP-6963 wallets are offered by name (`pickWallets`, unit-tested). E2E: two announced wallets, the chosen one connects |
| R-05 | A wallet "speed up / cancel" replacement could be reported as success: viem resolves `waitForTransactionReceipt` with the *replacement's* receipt, even when it was a cancellation or a different call | Reading viem's `waitForTransactionReceipt` source | **Fixed.** Only "repriced" counts; "cancelled"/"replaced" are reported as not having happened. Receipt waits time out at 3 minutes with curated copy. Unit-tested (`replacementOutcome`, timeout mapping) |
| R-06 | Mobile CLS 0.15: `main` moved 162 px on first load | Lighthouse CLI 12.6 trace (`LayoutShift` events) | **Fixed.** CLS 0 on mobile and desktop. Root causes are in DESIGN.md "Layout stability" |
| R-07 | `forge lint` `reentrancy-events` warnings after adding `MerkleProof` | `npm run lint:sol` | **False positive, triaged.** The deployed bytecode has no CALL-family opcodes. Suppressed inline with the reason (SECURITY.md) |
| R-08 | The Ledger said "Not on list" to allowlisted voters who hadn't claimed yet | Review of the new feature against existing screens | **Fixed.** It now says "Check allowlist", and eligibility shows in the row's record |
| R-09 | Firefox E2E can't launch here: the Playwright Firefox build fails with "side-by-side configuration is incorrect" (a missing Microsoft Visual C++ runtime) | `npm run test:e2e -- --projects=firefox` | **Blocked by the environment.** Needs a system runtime install (an admin action I didn't take). The same tests pass on Chrome, WebKit, Pixel 7 and iPhone 14 |
| R-10 | A real MetaMask extension isn't exercised | — | **Blocked.** Onboarding MetaMask means creating a wallet and setting a password inside a third-party extension, which I won't do on the user's behalf. MetaMask's protocol behaviour (lock state, 4902 add-chain-then-switch, accounts emptied, EIP-6963) is covered by stub-provider E2E tests through the real injected connector. A manual checklist is in VERIFICATION.md |
